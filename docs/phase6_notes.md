# Phase 6 Notes — Threshold Calibration and Evaluation

## 1. Scope and methodology

Phase 6 is an analytical calibration pass over the existing Phase 5
pipeline. No detector logic was changed; no ground truth, injection, or
test windows were altered. The analysis runs against the 10 rows in
`detection_events` joined with `ground_truth` (the controlled 10-window
experimental ground-truth set).

All numbers below are regenerated by:

```
python3 evaluation/phase6_evaluation.py
```

which writes `results/phase6/threshold_sweep.csv`,
`results/phase6/metrics.json`, `results/phase6/per_drift_type.csv`,
`results/phase6/per_column.csv`, `results/phase6/score_distributions.csv`
and plots `roc_curve.png`, `pr_curve.png`, `score_distribution.png`.

The threshold sweep is evaluated two ways, deliberately kept separate:

- **unified-only**: `DRIFT` if `unified_score >= threshold`.
- **final policy**: the Phase 5 `decide()` with the max-confidence
  overrides (schema/semantic/statistical score == 1.0 forces DRIFT).

## 4. Selected threshold decision: keep 0.5 as a placeholder

The empirically "best" threshold (0.06) is **not selected** because the
evidence does not support it:

1. **Knife-edge instability.** At 0.06, separation rests entirely on
   window_004 (0.0628) vs window_009 (0.0533) — a 0.0095 gap. Adjacent
   grid points flip hard: 0.05 gives 2 FP (F1 0.875), 0.07 gives 1 FN
   (F1 0.923). F1 = 0.875 -> 1.0 -> 0.923 across three consecutive
   thresholds.
2. **Threshold 0.06 sits inside the clean statistical band.** With
   schema=semantic=0, unified = statistical/3, so unified 0.06 maps to
   statistical ~0.18, which is **below** the clean-window statistical
   range (0.12-0.25 from the Phase 5 tuning pass; observed clean max
   0.160 here). A threshold of 0.06 would flag clean windows as drift on
   a broader sample. It overfits window_004.
3. **10-window dataset.** A single window changes every metric; no
   threshold selected from 10 windows is statistically defensible.

**Decision: leave threshold = 0.5 as the placeholder** in
`detectors/unified.py` (with the max-confidence overrides). More
validation data is required before replacing it. No decision-layer code
was changed in Phase 6.

Findings:

- The statistical_score (0.165) is only 0.005 above the clean max
  (0.160) and sits well inside the Phase 5 tuning-pass clean band
  (0.12-0.25). It is **not reliably separable** from the clean-window
  score distribution under the Phase 5 max-over-columns aggregation.
- At the **per-column level**, temp KS (0.259) exceeds the clean temp KS
  values (0.176-0.194), suggesting a weak per-column signal exists — but
  with 4 observations this is not statistically confirmed, and the
  signal is masked in the max aggregation by the co/lpg/smoke sampling
  noise floor (~0.40-0.50).
- Statement per the analysis requirement: "Variance-shift detection is
  currently not reliably separable from the clean-window score
  distribution under the Phase 5 max-over-columns aggregation." This is
  a limitation of the current aggregation, not evidence that variance
  drift is fundamentally undetectable.

**Stated decision (unchanged from Phase 5):** variance-shift detection
under max-over-columns aggregation remains an **accepted known
measurement limitation**. Candidate Phase 7 fixes: per-column thresholds
against each column's own no-drift distribution, or same-size reference
comparisons.

## 10. Statistical normalization assessment

The current constants (empirically derived, frozen in
`configs/thresholds.yaml`):

- KS_FLOOR = 0.50 (max-ks above the clean upper range)
- PSI_SCALE = 72.0 (clean max-psi 17.9 -> ~0.25)
- CHI2_SCALE = 32.0 (clean max-chi2 7.9 -> ~0.25)
- STATISTICAL_DECISION_THRESHOLD = 0.25 (clean score band upper
  bound; see section 13)

Effects observed on the 10 windows: clean statistical scores 0.12-0.16;
category shift and unit conversion saturate at 1.0; medium mean shift
scores 0.188 (compressed, just above clean); variance shift scores
0.165 (indistinguishable from clean). The compression of medium-severity
temp-only drift into the 0.16-0.19 region is caused by the
max-over-columns aggregation masking temp's signal behind noisier
columns — the scales themselves are not the primary cause. **Recommend
keeping the current normalization for the next phase**; do not silently
replace it. If temp-only statistical drift becomes a priority, move to
per-column thresholds.

## 11. Dataset-size limitations

- 10 controlled windows (7 DRIFT, 3 NO_DRIFT). Every metric is dominated
  by single windows; threshold selection is unstable (section 4).
- ROC-AUC / PR-AUC of 1.0 are artifacts of this small set, not evidence
  of production separation.
- Claims are limited to "controlled validation on the 10-window
  experimental ground-truth set." No production accuracy claim is made.

## 12. Recommended next step

1. Generate more controlled windows (multiple severities, more clean
   controls) to stabilize threshold selection; revisit whether 0.5
   should be lowered and by how much.
2. Evaluate per-column statistical thresholds against each column's own
   no-drift distribution to recover mean/variance-shift signals.
3. Compare combination methods (override + calibrated vs plain average)
   as candidate decision policies on the larger set.

## 14.11 Distribution shift is a second known, FLAGGED limitation (follow-up)

Phase 6 follow-up verification confirmed that distribution shift
receives the **same "expected false negative — known aggregation
limitation"** treatment as variance shift, through the identical
flagging mechanism (no new scheme invented). This section exists so
the Failure Analysis section writer has both limitations documented
in one place.

### Why it is a known limitation

Under max-over-columns statistical aggregation, distribution-shift
windows (power-transform injection on temp) are unresolved at every
severity: the per-column temp KS signal is real but weak (temp
ks_max 0.448 clean -> 0.461 / 0.461 / 0.474 for low/medium/high;
ks_med 0.257 -> 0.253 / 0.267 / 0.293) and PSI does not move. The
signal stays below the frozen ks_floor (0.50) and is masked by the
co/lpg/smoke sampling-noise floor — structurally the same root cause
as variance shift. It is documented as a limitation, NOT fixed in
Phase 6 (out of scope; a Phase 7+ aggregation question, e.g.
per-column thresholds).

### Where the flag now appears (mirrors variance shift exactly)

| location | variance shift | distribution shift |
|---|---|---|
| `experiments/tuning_results.json` per-condition flags | `expected_false_negative: true` for variance_low/medium/high | `expected_false_negative: true` for distribution_low/medium/high |
| `experiments/tuning_results.json` `known_limitations` | `variance_shift_aggregation` | `distribution_shift_aggregation` (same flag string, own reason) |
| `results/phase6/threshold_derivation.md` separation table | `expected FN = yes` | `expected FN = yes` |
| ground-truth CSV / Postgres DDL / loader | `expected_false_negative` column; window_005 (variance) carries the flag | mechanism is drift-type-agnostic; see note below |

### Ground-truth CSV note

The controlled 10-window stream (`drift_injection/stream_builder.py`)
contains no distribution-shift window — its statistical windows are
mean shift (window_004), variance shift (window_005), and category
shift (window_006). There is therefore no distribution row in
`results/raw/ground_truth.csv` to flag. The flagging mechanism itself
(`create_event(..., expected_false_negative=...)`, the
`expected_false_negative` column in `GROUND_TRUTH_COLUMNS`,
`docker/postgres_schema.sql`, and `experiments/load_ground_truth.py`)
is drift-type-agnostic: any window injecting an aggregation-limited
drift type — distribution shift included — must be created with the
same flag string `"expected false negative — known aggregation
limitation"`. This is stated in a comment at the flag site in
`stream_builder.py` so Phase 7's window generation reuses it.

### Flagging rule (single source of truth)

`experiments/tuning_pass.py` exposes
`expected_false_negative_condition(condition)` — True for
`variance_*` and `distribution_*` conditions — and
`expected_false_negative_reason(condition)`. Both limitations share
the flag constant `EXPECTED_FN_AGGREGATION_LIMITATION`; each keeps
its own machine-readable reason. Phase 7 should consume the flag
generically across drift types, not per-type, so neither limitation
silently penalizes the detector in precision/recall.
